# Delegated forum topic publication — candidate, not activated
Owner opt-in from a verified forum session: explicit checkbox, 24-hour grant, immediate revocation. Only new text topics are permitted; normal three-topic daily and sixty-second limits remain. No replies, editing, deletion, private account access, password, JWT minting, service-role API, automatic translation consent or API billing. The owner is not inferred from a chat identity; the authenticated owner creates the grant and the server derives the author solely from it. Public topics disclose AI assistance in their source language. Never invent user experiences, endorsement, measurements or sources.
The database candidate creates an RLS-protected grant table and a non-exposed private audit and a fixed-search-path SECURITY DEFINER publisher callable only through the dedicated NOLOGIN, NOBYPASSRLS execution role selected explicitly by the existing postgres connection. No new login, password or browser role is created. The executor is granted only private-schema USAGE and this function's EXECUTE, not direct topic, grant, audit or auth-table access. The function checks session user and selected execution role, plus live owner-issued grant and originating session. It does not extend admin privileges to browsers or expose a new privileged public RPC. Existing direct authenticated inserts still require matching auth.uid(), original RLS and quotas. The additional trigger path requires a matching private audit record from the same transaction; only the private publisher is the supported administrative path. No synthetic auth.uid() in production. Owner eligibility and originating session existence are checked at publication. Revocation and publication serialize on the grant row. Same request ID/payload returns the existing topic; conflicting reuse is rejected. Translation consent is always false. Never publish using raw admin inserts.
The candidate SQL is intentionally in supabase/sql, not auto-applied. First run the isolated disposable PostgreSQL regression, review ACL/RLS and verify Supabase Data API exposure and current triggers against production. Review the account-consent UI and test browser flow (guest, opt-in, revoke, account change, errors). Run security checks before merging. For activation use a separately reviewed migration/rollback in the real project, confirm grants are inaccessible to anon/other accounts, confirm owner-visible status, apply only with the verified database version and no schema drift, run advisors, then deploy UI. No grant is issued by an admin and no production topic should be created as a test. User must sign in and explicitly opt in before use. Disable with rollback (revoke grants, remove private publisher, restore prior trigger, keep audit and previously published content).

For an authorized publication, use a single transaction: `BEGIN; SET LOCAL ROLE tc_forum_assisted_executor; SELECT * FROM tc_assisted_private.publish_topic(...); COMMIT;` only after verifying the intended owner and grant in a separate read-only query. Do not issue a direct administrator INSERT or change session/JWT claims. Isolated tests cover the scoped execution role, reject direct admin function calls and enforce ordinary account isolation. Production rollout must verify effective ACLs, since inherited PUBLIC grants vary by database.

## Owner-only activation (25 November 2026)
The separate `supabase/sql/forum_assisted_owner_only.sql` migration creates a one-account allowlist; the operator supplies the verified owner UUID in the session setting `tc.assisted_owner_id` before applying (production identity is not committed). The database independently blocks every other account from creating, reading or revoking assisted grants; the private publisher rechecks eligibility at publication time. Existing unrelated grants are revoked, the owner's grant remains intact. The client fails closed unless the signed-in user receives their own allowlist row. Ordinary forum posting remains unchanged. Keep the owner restriction even when rolling back UI changes; do not restore general eligibility. To disable the feature entirely, remove the allowlist row and revoke the owner's grant transactionally.
