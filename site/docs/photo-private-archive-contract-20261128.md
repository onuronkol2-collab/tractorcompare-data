## Pending manifest recovery and pre-acquisition guards (DEVAM follow-up)

The private runner records the intended immutable manifest digest and parent locally before the manifest POST. A pointer update failure leaves the pending journal intact. Explicit recovery checks the existing head, exact local ledger digest and every archived original; it may seal the exact pending manifest if missing, but never performs a provider request. If an original upload fails before journaling, retain the original workspace and ledger for explicit recovery; this is not automatically repaired. The local journal is not a remote authoritative head or cross-machine lease. Do not run multiple private writers.

Fresh Commons requests from the private runner are deferred until a genuine shared cross-runner reservation and serialization mechanism is verified; environment flags alone are not a lease. Cached originals are still eligible for revalidation. Independent reviewed acquisition requires a recent free capacity observation and conservative remaining-byte reserve for the expected original and maximum manifest. This is a local spending guard, not actual plan or remaining-capacity verification. No bucket, service credentials, or ordinary user policy was provisioned. Five additional regression cases were drafted; TEST is required.

## Original-upload interruption recovery (DEVAM)

The local pending manifest journal now precedes all remote original writes, not only the manifest write. Validate all local originals first. Recovery validates the exact parent and intended digest, then may upload only missing content-addressed originals from the matching local workspace and seal the exact intended manifest. Journal/pointer directory entries are synchronized before proceeding. POSIX directory flock prevents competing operations in the same local output workspace; this is NOT distributed locking, cross-workspace coordination or a remote head CAS. A dedicated single private writer remains mandatory. Four regression drafts cover journal ordering, missing original recovery, same-workspace contention and corrupt parent rejection. No tests or remote storage operations performed.

## Dedicated access policy preparation (DEVAM)

`photo-private-archive-policy.py` generates review-only SQL after an independently verified dedicated archive Auth UUID is supplied. It does not connect or execute. Two permissive grants allow that nonanonymous identity to read and insert only SHA256-addressed original and manifest keys. Four restrictive policies preserve other buckets' existing policy behavior while preventing broad future anon/authenticated policies from exposing or mutating the archive. No UPDATE or DELETE grants, no service-role credential, no user-editable metadata. The client now requires the explicit nonanonymous JWT claim rather than assuming an absent claim is safe. Three additional regression drafts are required by the Python runner. Actual PostgreSQL/RLS acceptance, authenticated Storage API behavior (including list versus download), dedicated account isolation from forum permissions, and the real JWT shape must be verified during TEST. Policy SQL is not a migration and must not be executed without checking live RLS, bucket privacy and rollback. Supabase documentation: https://supabase.com/docs/guides/storage/security/access-control and https://supabase.com/docs/guides/storage/buckets/fundamentals. Changelog markdown endpoint was unavailable to the web reader; no feature version assumption or remote change was made.

Never use an empty local directory or a permission-filtered Storage list as evidence that the remote archive is empty. Do not accept a new genesis after an archive has been initialized. A distributed authoritative head/lease and shared Commons cross-runner budget remain separate prerequisites for unattended acquisition.
