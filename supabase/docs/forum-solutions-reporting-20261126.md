# Forum solution and reporting foundation (2026-11-26)

This additive candidate is deliberately separate from production deployment and existing member permissions.

- One solution per published question or maintenance topic. Only the authenticated, non-anonymous topic author may select, replace or remove a published reply belonging to that topic. The public selection disappears if the reply or topic is moderated. The author can repair a stale selection without access to the hidden reply body.
- Content reports contain only fixed reason codes, target identifiers and authenticated reporter identity. A member can submit once per target. No visitor/member report-list access, no user-controlled status or reporter identity, and no automatic removal of content. Trusted server-side moderation is the only reader. No new public service-role access.
- This is not a completed moderation dashboard, notification service, or anti-spam system. A concurrency-safe UTC daily quota of ten successful reports per account uses a private transactional counter; rejected reports consume no quota. Before exposing report controls, add the trusted moderator authorization workflow, bounded retention and concurrent-load verification. Before exposing solution controls, validate exact API projection, all ten locales, owner/session switching, hidden-reply behavior and browser regression. No new paid service.
- Run the disposable PostgreSQL 17 workflow first. Its data is synthetic and never copied to production. Before any production application check current relation shape, grants, RLS, PostgreSQL version, absence of conflicting objects, and deployment compatibility. Apply in a transaction and separately verify grants, policy definitions and anonymous visibility. Do not claim deployment from a passing fixture. Preserve any actual user records before invoking rollback; the rollback file is for the new tables only.

## Incident prevention: SQL delimiter corruption (26 November 2026)

The failing fixture contained four DO blocks with single-dollar delimiters caused by JavaScript replacement-string interpolation of double dollar characters. Use literal callback replacements (`source.replace(anchor, () => replacement)`) or safe whole-file edits. Verify the final checked-in content, run `node scripts/check-sql-dollar-delimiters.mjs --self-test <changed SQL files>`, then run the actual PostgreSQL fixture and rollback. A separate fast PR workflow checks changed SQL files across the repository; it is a focused lexical guard, not a full SQL parser or a substitute for real database tests. The isolated job logs file names and psql line numbers and checks server readiness as the actual postgres user. The quota trigger runs after successful inserts so ignored duplicate inserts consume no quota; the fixture verifies that behavior.

The subsequent container initialization failure was Docker exit 125: the Actions runner did not preserve a single-quoted multiword health command as one argument. Keep the health command as the single token `pg_isready` and set `PGUSER` and `PGDATABASE` in the disposable service environment. Do not rerun the broken configuration unchanged. Verify the isolated job reaches its SQL fixture before declaring the incident resolved.

## Staged solution release (26 November 2026)

The exact accepted-solutions prefix of the independently tested candidate is available as `supabase/sql/forum_accepted_solutions_release.sql`. Production preflight verified PostgreSQL 17, both existing RLS-protected UUID tables, existing public policies, and absence of the target. The solution-only migration was applied; RLS, five policies, anonymous SELECT without INSERT, authenticated reply-column UPDATE without topic-column UPDATE, and anonymous empty-table reading were verified. No report table or report-writing permission was deployed. The new topic UI uses separately confirmed anonymous selection and authenticated ownership, original reply identifiers, conditional mutations, and ten localized strings. UI delivery requires passing CI and actual Cloudflare release verification. Report ingestion remains gated until moderator authorization, retention and concurrent-load checks are ready. Never reapply the combined candidate after this staged migration; prepare a separately tested report-only release instead.
